# Jouzu v0.1.9

Unreleased.

## One coordinator for automatic turns

A session can produce work on its own: a background task finishes, a goal or measured loop wants to continue, a scheduled prompt fires, a child agent reports a result, or context compaction is requested. Jouzu v0.1.9 adds a session flow controller that decides what reaches the model, when, and in what order. It is on by default.

The controller changes when automatic work runs:

- A completion that arrives while the agent is working waits until the current turn and any queued messages finish.
- Completions that are ready at the same time are delivered in one turn instead of one turn each.
- Each wait records the work it depends on and a deadline. A background task that declares a health policy reports whether its process is still alive, so a wait does not hang on a job that has already stopped.
- Automatic work from other sources — child agents, scheduled prompts, and task-list advances — is held while a wait is live rather than interrupting it.

Set `JOUZU_FLOW_CONTROL=0` to start a session without the controller.

Finished results, settled attempts, and superseded history are retired under fixed limits, so a session that runs many automated turns does not grow without bound. Evidence needed to explain a hold is kept.

## Inspecting and repairing with /flow

`/flow` shows what the controller is holding and lets you repair it. Its output goes to the terminal and adds nothing to the model's context. The command reports up to seven groups:

| Group | Meaning |
| --- | --- |
| Waiting | Live waits, with the work they belong to, their unmet dependencies, and their deadline |
| Held input | Work the controller is holding, with the reason |
| Withheld requests | Requests whose input was incomplete, with the retry command |
| Interrupted, outcome unknown | Turns whose result was never recorded |
| Active work | Work that can still take automatic turns, with its pause and stop commands |
| Held work | Work you paused or stopped |
| Not accounted for in this session | Work a loaded extension still names that this session does not control |

### Commands

- `/flow retry <request>` sends a request again after its input was withheld. The retry is bound to the exact input that was held, so it cannot run against changed content.
- `/flow cancel <token>` cancels a wait so it stops blocking. The job the wait was watching keeps running.
- `/flow pause <work>` and `/flow resume <work>` hold and release the automatic turns of the named work, such as a running goal or measured loop. Paused work keeps its state and takes no automatic turns until you resume it.
- `/flow stop <work>` retires the named work and ends its waits. A job it already started keeps running.
- `/flow resolve <attempt> retry|discard` decides a turn that was interrupted between sending a request and recording its result. Jouzu cannot tell locally whether the provider answered it, so it waits for you. `retry` makes the work eligible again and may repeat a turn the provider already answered; `discard` accepts it as spent.

Identifiers are printed whole, so you can copy a command directly from `/flow` output.

## Save catalog tokens in Settings

Settings / Catalogs can store a bearer token directly, without an environment variable. Add or edit a source, choose `Bearer token`, and enter the token in the masked **Token** field. The token is saved in `catalog-credentials.json` next to `catalogs.json` with private file permissions, keyed to its source, and never shown on screen. An environment variable with the same name takes precedence, so exporting one overrides the saved token.

A bearer source whose variable is not yet set can be saved. Jouzu warns in the source list and in the selected source's detail instead of blocking, stores the source without contacting it, and refreshes it once the variable is set or a token is saved. Removing a source, or switching its authentication to none, removes its saved token.

## TextGuard review and persistent approvals

The `/textguard` review is one screen. The list shows each withheld item and non-blocking report with its source label; selecting one opens a detail view with the findings and their locations, and the flagged content shown with control and invisible characters escaped. `PageUp` and `PageDown` scroll the view, and Escape returns to the list.

Only content-blocking findings raise a session notification. Warnings and informational reports stay inspectable through `/textguard` and can be dismissed for the session.

The detail view offers two approvals:

- **Allow for this session** admits the content for the current session.
- **Always allow this exact content** records a persistent approval for those exact bytes.

Persistent approvals are keyed by the content's SHA-256 digest, the scanner identity, and the policy version. A change to the content, the scanner, or the policy requires a new decision. The store is bounded to 128 records and holds no source text, paths, or labels; delete it to revoke all persistent approvals. Child agents do not share the store and cannot create approvals.

## Other changes

- Background-task results are kept when the task is cleared.
- `/flow` no longer reports input that was already delivered as held.
- An RPC session finishes an accepted prompt when its input stream ends.
- Child agents receive the same model-specific behavior guidance as the parent session.

## Testing limits

Session flow control is newly on by default. The deterministic suite substitutes the provider, and the live-model smoke is opt-in, so behavior under real workloads still needs dogfooding. See [docs/testing.md](https://github.com/shisa-ai/jouzu/blob/main/docs/testing.md) for the suites and the live smoke.
